# Ручная матрица приёмки опубликованного файла

Workflow `Published binary acceptance` запускается только через
`workflow_dispatch`; push и PR сами его не запускают. Матрица использует
стандартные `ubuntu-latest`, `windows-latest`, `macos-latest` публичного
репозитория, без larger/self-hosted/платных runner. По
[документации GitHub](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
стандартные hosted runner в публичных репозиториях бесплатны. `latest` означает
актуальный стабильный образ GitHub, а не обязательно самую новую ОС производителя.

SDK закреплён на 11.0.100; checkout, setup-dotnet и upload-artifact закреплены
полными SHA официальных action. Восстановление пакетов использует lock-файлы.
Каждое задание и рискованный шаг имеют timeout; новый запуск той же ветки
отменяет предыдущий через concurrency. Общий предел задания — 15 минут.
Артефакты автоматически удаляются через три дня.

Для регистрации ручного запуска GitHub также требует наличие workflow в
[default branch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
Поэтому main получает только тот же файл workflow как технический bootstrap;
реализация и испытания остаются в develop. Фактический запуск выбирает
`--ref develop`. Workflow сам не меняет default branch и не сливает код в main.

Каждая ОС определяет собственный RID через `dotnet --info`, поэтому архитектура
macOS не предполагается заранее. Выполняются сборка решения, проверка генерации
контракта, тесты хранилища, затем self-contained single-file публикация сервера
и отдельной fixture.

`scripts/run-published-acceptance.py` копирует **только один файл сервера** в новый
пустой каталог и аналогично fixture в другой каталог. Запускает собственный
сервис на случайном loopback-порту со случайным ключом в окружении, а не argv.
Ключ передаётся HTTP-harness через приватный файл; SDK нужен только самому
испытательному harness. Отдельно установленный .NET не используется как способ
запуска опубликованного сервера/fixture. Это проверяет автономность копии файлов,
но наличие SDK на hosted runner не является доказательством отсутствия runtime
на всей машине: такую проверку даёт чистая VM.

HTTP-harness проверяет отказ без/с неверным ключом, строгие запросы, разделение
потоков, поздний stdin, двоичный вывод, асинхронные задачи, полный spill/blob,
удаление и штатный drain. После drain процесс обязан штатно выйти; при провале
убираются только процессы, созданные этим испытанием. Linux дополнительно
проверяет настоящий Ctrl-C из собственного PTY тем же опубликованным бинарником.

Сохраняются SHA-256 входных бинарников, состояние ОС, отдельные результаты
проверок, exitCode и безопасные журналы. Случайный ключ и приватный рабочий
каталог в артефакты не входят. Любое обнаружение ключа в выводе делает приёмку
красной; копии журналов перед публикацией дополнительно заменяют этот ключ.

Локальный запуск уже собранных файлов:

```sh
python scripts/run-published-acceptance.py \
  --server-binary /path/to/exec-server \
  --fixture /path/to/exec-server-fixture \
  --harness tools/ExecServer.Harness/bin/Release/net11.0/exec-server-harness.dll \
  --dotnet /path/to/dotnet
```

Windows hosted runner — это Windows Server. Он **не заменяет** отдельные
испытания Windows 10/11 на VM владельца. Успех одной клетки не переносится на
другую; реальный итог устанавливается по exact-head квитанциям конкретного запуска.
Само наличие этого workflow не означает, что матрица уже выполнена.

## Первый фактический запуск

[Run 43777442558](https://github.com/dmitry-ra/exec-server/actions/runs/43777442558),
ревизия `d9832c18b727fdf9a941d0608453d24e07c46e73`:

| Платформа | Фактический результат |
|---|---|
| Ubuntu hosted | 17/17 HTTP, затем 4/4 lifecycle; job SUCCESS |
| Windows hosted | 17/17 HTTP; job SUCCESS |
| macOS 26.7.2 ARM64 | 16/17 HTTP; job FAILURE |

На macOS отказала только подготовка проверки закрытого stdout: fixture не
подтвердила EOF до начала long polling. Сборка, генерация, хранилище,
публикация, остальные проверки и штатный выход сервиса прошли. Эта квитанция
не доказывает ошибку самого long polling: сначала требуется установить, почему
fixture не закрыла все writer-дескрипторы. Mac-клетка этим запуском не принята.
