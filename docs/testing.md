# Проверка ExecServer

Проверяется первая версия с pipes. Терминал, PTY/ConPTY, интерактивные меню и
восстановление после перезапуска не входят в эту приёмку. Главный критерий:
готовый исполняемый файл копируется на целевой сервер и работает без SDK и
отдельно установленного .NET runtime. Сборка исходников требует SDK; запуск
готового self-contained файла — нет. Системные библиотеки целевой ОС остаются
обычными требованиями платформы .NET.

## Структура испытаний

- `tests/ExecServer.Fixture` — детерминированная дочерняя программа без shell и
  внешних утилит. Умеет раздельный вывод, двоичные данные, ожидание, echo до EOF,
  большой вывод, отложенный вывод и заданный код завершения.
- `tools/ExecServer.Harness` — отдельное консольное приложение C#, обращающееся
  к живому сервису по HTTP. Использует сырой JSON, а не серверные DTO. Результат
  — одна JSON-строка с отдельными проверками, длительностью и ошибками; ненулевой
  код завершения означает провал.
- Модульные проверки хранилища отдельно проверяют переключение памяти на файл,
  конкуренцию, ожидание новых данных и освобождение ресурсов.

Harness не печатает API-ключ, HTTP-заголовки и окружение запуска. Он запускает
собственные дочерние программы и удаляет только принадлежащие ему записи
исполнения. Полный публичный лог сессии не требуется для публикации результата.

## Локальный сквозной прогон

Из корня репозитория:

```bash
bash scripts/install-sdk.sh "$PWD/.sdk"
.sdk/dotnet build tests/ExecServer.Fixture/ExecServer.Fixture.csproj
.sdk/dotnet build tools/ExecServer.Harness/ExecServer.Harness.csproj
```

В отдельном терминале запустите сервис с новым тестовым ключом. Конкретный
ключ передаётся окружением; в репозитории ключей нет:

```bash
export EXECSERVER_API_KEY="$(openssl rand -hex 32)"
export ExecServer__MemoryThresholdBytes=32768
export ExecServer__InlineBytes=4096
export ExecServer__MaxReadBytes=65536
export ExecServer__MaxWaitMilliseconds=5000
.sdk/dotnet run --project src/ExecServer -- --urls http://127.0.0.1:5080
```

Из второго терминала, имеющего тот же тестовый ключ:

```bash
.sdk/dotnet tools/ExecServer.Harness/bin/Debug/net11.0/exec-server-harness.dll \
  --url http://127.0.0.1:5080 --token "$EXECSERVER_API_KEY" \
  --fixture "$PWD/tests/ExecServer.Fixture/bin/Debug/net11.0/exec-server-fixture.dll" \
  --dotnet "$PWD/.sdk/dotnet"
```

Опция `--dotnet` относится к пути запуска fixture **на машине сервиса**. Для
удалённой проверки пути `--fixture` и `--dotnet` должны существовать на целевой
машине. Можно вместо DLL скопировать self-contained fixture и не передавать
`--dotnet`. Самому сервису SDK для этого не нужен.

Обычный harness не останавливает сервис. Для последнего, отдельного прогона
добавьте `--include-shutdown`: он проверит переход в draining, отказ нового
запуска и возможность дописать stdin уже работающей программе. После окончания
последнего управляемого процесса сервис должен завершиться; проверять его
успешный HTTP-ответ после завершения не требуется.

## Что проверяет harness

1. Без ключа и с неверным ключом status, list, launch, output/blob, stdin/EOF,
   signal, diagnostics, delete и shutdown отвечают 401. Разрешённый probe
   дополнительно проверяет, что запрещённый launch не создал marker.
2. Противоречивые text/base64, неверный base64 и неизвестные поля запроса
   отвергаются до создания дочернего процесса.
3. stdout и stderr возвращаются раздельно, с правильными счётчиками и exit code.
4. Начальный и последующий stdin сохраняют порядок; закрытие stdin даёт EOF.
   Двоичный stdin проходит без изменения байтов.
5. Асинхронный ID виден в listing, диагностический снимок содержит root PID.
6. Пропущенный offset повторяет чтение с начала; явный offset и limit дают
   правильные bytes/nextOffset/remainingBytes.
7. Неверный UTF-8 возвращает ошибку с накопленной длиной, а последующее чтение
   base64 подтверждает, что ошибочное текстовое чтение ничего не уничтожило.
8. Два MiB вывода сохраняются полностью; blob читается порциями по 4096 байт.
   При указанных настройках это также проходит через spill на диск. При других
   порогах следует отдельно обеспечить их пересечение, иначе утверждать spill
   по одному успешному чтению нельзя.
9. durable сохраняет вывод после чтения до DELETE; обычный окончательный хвост
   удаляет весь запуск. Range-coverage не отслеживается.
10. Long polling просыпается при новом выводе, а не только по окончании timeout.
11. Unix SIGTERM выполняется на Unix; Windows явно отказывает в Unix-сигнале.
12. Отдельный заключительный прогон проверяет draining.

Число успешных проверок само по себе не доказывает правильность: каждый случай
должен падать при соответствующем дефекте — отключённой авторизации, объединении
потоков, усечении вывода, раннем удалении или отсутствии пробуждения.

## Приёмка на чистой Linux-ВМ

Воспроизводимый сценарий лаборатории должен создавать **новую собственную** ВМ,
а не переиспользовать сервер владельца или давно настроенный стенд. Адрес,
имя, путь образа и ключ доступа являются параметрами локального стенда и не
публикуются как инфраструктура владельца.

1. Закрепить образ Ubuntu URL и хешем, записать имя/ресурсы созданной ВМ и
   изменения хоста. Использовать существующий механизм лаборатории вместо
   второго самодельного provisioner, если он доступен.
2. Скопировать self-contained ExecServer и fixture, задать новый тестовый ключ,
   привязать REST к localhost. SSH используется для первоначальной доставки и
   запуска процесса, затем только для туннеля и независимой сверки результата.
3. Убедиться, что `dotnet` отсутствует и готовый сервис всё равно запускается.
   Прогнать harness через SSH-туннель; никакой прямой публичный bind не нужен.
4. Скопировать исходники проекта. Через POST /v1/executions запускать отдельные
   команды установки системных зависимостей и SDK, восстановление, сборку и
   тесты. Для долгого шага получать ID, затем опрашивать состояние и вычитывать
   оба потока до конца. Если нужны shell-операторы, запускать `/bin/bash` как
   обычную программу с явными аргументами.
5. Требующие sudo операции запускать только на собственной ВМ. При разрешённом
   stdin-режиме sudo использовать `sudo -S`; обычный terminal prompt в pipes
   не обещается. Пароль не включать в argv/публичные журналы.
6. Полученный в ВМ бинарник проверить тем же harness. Сохранить версии, хеши,
   exit codes и отдельные результаты; сверить их независимо через SSH.
7. Остановить только созданные лабораторные процессы, убрать туннель и выполнить
   описанную владельцем лаборатории процедуру удаления собственной ВМ. Удаление
   чужих ВМ или дисков не входит в сценарий.

## Матрица ОС и граница готовности

| Среда | Минимальная проверка |
|---|---|
| Актуальный Ubuntu Linux | Полный harness, single-file без runtime, чистая ВМ, установка зависимостей и сборка через REST |
| Windows 10 | Self-contained win-x64, stdin/EOF, раздельные двоичные потоки, storage, отказ Unix-сигналов |
| Windows 11 | Тот же harness на отдельной реальной ОС |
| Актуальная macOS | Явно запущенный GitHub Actions workflow, сборка и harness; платные минуты не разрешены |

У каждого workflow должны быть timeout и concurrency. Выпуски, теги и PR не
создаются этим harness. Успешная локальная сборка не означает, что проверена
вся матрица или достигнут критерий «скопировал и работаешь».
